# 幕间当前技术架构

## 2026-10-05：多规格商品增量（当前32张表）

在评价增量的29张表基础上增加 `product_variant`、`variant_cart`、`order_variant` 三张表，旧表采用 `CREATE TABLE IF NOT EXISTS` 增量创建，不删除既有用户、商品、购物车或订单。`ProductVariants` 统一负责规格配置、选款、汇总库存和版本校验；`ShoppingController` 将旧默认购物车与规格购物车合并返回；`CommerceOrders` 保存规格快照，并在取消/到期时按原规格返库。

父商品行是规格编辑、购买和返库的共同锁。保存要求商品 `version` 未变化，已有规格只能改名、改价或停售；购买按商品再按规格顺序锁定，使用服务端规格价格并检查 `expectedPrice`；批量结算的锁顺序为商品ID、规格ID，失败时整批回滚。父商品价格同步为在售规格最低价，库存同步为在售规格库存之和；无规格商品沿用旧字段。

当前支持手动填写的组合名称（每商品最多20种），不把颜色、容量拆成独立属性表。下单幂等键和购物车批次指纹包含 `skuId`，`order_variant` 保存购买时名称，确保改名/停售不改变历史。详细契约、演示商品、截图和验收见[多规格说明](13-多规格商品与库存.md)。

## 2026-10-04：评价增量（历史29张表）

新增 `ProductReviewController` 与 `product_review` 表；`(order_no,product_id)` 联合唯一、评分1–5校验、关联订单/商品/买家的外键。提交锁本人订单，检查商品和COMPLETED状态，再以当前读校验重复，保证并发只落一条评价；服务端裁剪首尾空白并返回中文400/404/409。

公开查询用只读事务统一评价列表及聚合统计，仅返回VISIBLE记录；最近100条按时间与ID倒序。GET `/api/mall/products/*/reviews` 显式放行，其余个人接口保持登录校验。公开DTO不含订单号及买家ID。订单返回新增 `reviewed` 布尔字段；前端 `ProductReviews` 复用到详情和订单弹窗，独立处理公开数据/待评价资格的加载失败。

新表通过 `CREATE TABLE IF NOT EXISTS` 创建，不删除旧订单或店铺；本轮无需修改旧表字段。状态HIDDEN预留，无评价审核接口，不等于已交付审核功能。[契约与验收](12-商品评价闭环.md)。

## 购物车与地址架构（这一阶段28张表，后续评价为29张）

新增 ProductDetails、ShoppingController、ShoppingDemoData，扩展原商城/订单服务。前端新增 Shopping.tsx、shopping.css；路由为#cart、#addresses、#product-favorites，订单详情用独立弹窗。结算内地址编辑用React Portal，避免嵌套表单误提交。

新增7表：shop_product_detail、shopping_cart、shipping_address、product_favorite、checkout_batch、checkout_batch_item、shop_order_event。原21表不做删除式迁移，旧商品可不提供扩展资料。

购物车/地址/批次以用户行锁串行化；批量结算按商品ID顺序锁库存，先校验全部商品，再在同一事务中创建订单并删除选中购物车记录。buyer_id/request_key唯一约束和请求内容SHA-256指纹保证幂等。expectedPrice防止确认后价格变化；金额使用BigDecimal。订单状态事件与原状态操作同事务写入。公开销量来自COMPLETED订单聚合，无伪造数据。

[全部表约束、请求契约和边界](11-商城详版购物车与地址说明.md)。规格组合已在2026-10-05增量交付，真实支付、运费和店铺合单仍需后续扩展。

## 商城首版架构（当时21张表，历史扩展到29张，当前为32张）

前端新增 `Commerce.tsx`（商城/店铺/详情/结算/订单/视频商品袋）、`Merchant.tsx`（开店/商品/视频/发货）及独立响应式样式。Hash 路由为 `#mall`、`#product/{id}`、`#store/{id}`、`#orders`、`#merchant`、`#merchant/videos`；复用JWT、中文异常和模态框。

后端 `StoreController` 验证店铺与视频归属、资源链接、在售挂载，创建视频时同事务写短剧/剧集/店铺视频/商品挂载。`OrderController` 提供登录买家和店主接口；`CommerceOrders` 负责库存、快照、幂等和状态转换。

| 新表 | 约束与用途 |
| --- | --- |
| shop | owner_id唯一，一人一家店；ACTIVE/CLOSED |
| shop_product | 金额DECIMAL(10,2)、库存非负、上下架、version乐观锁 |
| shop_video | drama_id主键关联所属店铺，用于店主发布与挂载归属校验 |
| drama_product | drama_id/product_id联合主键和排序；服务层最多6件 |
| shop_order | 订单号唯一、buyer_id/request_key唯一；商品/地址快照、数量1–99、总金额DECIMAL(12,2)、到期时间、订单状态 |
| product_variant | product_id下的手动组合规格；价格、库存、on_sale和索引；已有规格不物理删除 |
| variant_cart | user_id/variant_id联合主键；规格购物车数量与更新时间 |
| order_variant | order_no主键；购买时规格编号和名称快照，规格外键RESTRICT |

下单事务先锁买家、检查幂等，再锁商品并校验库存；以数据库单价计算总价并扣减库存、写订单。取消、支付、发货、收货锁订单后校验归属及当前状态；返库递增商品版本。商品编辑携带version，冲突返回409，不覆盖并发扣减。订单到期按数据库时间判断，定时扫描每30秒最多100单，使用FOR UPDATE SKIP LOCKED；重复取消无二次返库。此实现仍为单体服务。

演示订单状态：PENDING → PAID → SHIPPED → COMPLETED；PENDING也可到CANCELLED。PAID是明确的模拟支付结果，不代表第三方渠道到账。公开商城API不返回收货人信息；订单按买家/店主隔离。MySQL启动建表对原16表版本增量创建5表，不需要删除已有数据。

## 新增发布链路

商城扩展前，发布与评论治理部分共16张表；加上商城首版5张表为21张，再加详版7张表、评价1张表和多规格3张表，当前共 **32张表**。发布相关表如下：

| 表 | 数据与约束 |
| --- | --- |
| `episode_release_plan` | 短剧、集号、标题、片源、北京时间目标对应的 Unix 毫秒、SCHEDULED/PUBLISHED/CANCELLED、已发布集 ID 与实际发布时间；状态/时间索引用于到期扫描 |
| `user_reservation` | 用户/计划组合主键，防重复预约；外键级联 |
| `user_notification` | 用户、分集、产生/已读毫秒；用户/分集唯一；用户/未读/ID 索引；下架分集级联删除消息 |
| `drama_comment_report` | 评论举报人、原因、处理状态和处理人；`(comment_id,user_id)` 联合唯一，避免重复举报 |
| `drama_comment_moderation` | 评论当前状态 `VISIBLE/HIDDEN`、处理原因、管理员和更新时间；评论一对一 |

排期独立于 `drama_episode`，公开日历不含视频地址；旧列表、详情、首集 URL、历史和离线接口继续读取已发布内容。关系删除时，已发布计划的 episode_id 设空，个人预约显示“本集已下架”。这是 API 层的发布隔离，不等于本地静态媒体的付费访问控制。

`ReleaseController` 处理排期管理、个人预约和信箱；`ReleaseService` 用 `@Scheduled` 扫描并通过 `TransactionTemplate` 发布。一次事务完成“锁短剧 → 锁排期 → 校验当前状态与集号 → 插入分集 → 标记已发布 → 更新连载/首集 → 插入提醒”。计划修改、取消、预约与立即发布均按相同父子锁顺序；集号冲突校验用 FOR UPDATE 当前读，避免 MySQL REPEATABLE READ 的旧快照漏掉并发新增计划。

发布时按当前追剧人和该集预约人做 UNION，并用 (user_id,episode_id) 唯一约束兜底。扫描和人工发布并发时只有一次生效；已发布再次请求返回成功，已取消请求立即发布返回 409。失败整体回滚、保留计划并记录日志，下轮重试。启动约 5 秒开始扫描，每 10 秒最多 50 条；目前没有重试退避、死信或批量运营工作台。

排期创建/改期仅接受未来一年内的毫秒时间；前端 datetime-local 明确按 +08:00 转换，展示固定 Asia/Shanghai，避免客户端本地时区和数据库会话时区偏差。`ReleaseDemoData` 在已知示例短剧尚无计划且未发布第 4 集时，仅初始化一次 4/5 集计划。

| 接口（均以 /api 开头） | 权限与请求 |
| --- | --- |
| GET /release-plans?dramaId= | 公开；最多 200 条待发布计划，登录后返回本人 reserved |
| GET /me/reservations | 登录；最多 200 条本人预约，含发布/取消状态 |
| PUT / DELETE /release-plans/{id}/reservation | 登录；幂等预约/取消，只能预约待发布计划 |
| GET / POST /admin/dramas/{id}/release-plans | 管理员；创建接收 {episodeNo,title,videoUrl,publishAt} |
| PUT /admin/release-plans/{id} | 管理员；改期或恢复，不能改变原集号 |
| POST /admin/release-plans/{id}/cancel 或 /publish | 管理员；取消/立即发布 |
| GET /me/notifications/count | 登录；unreadCount、throughId |
| GET /me/notifications?page=0&unread=false | 登录；20 条/页，返回 items、total、unreadCount、throughId |
| PUT /me/notifications/{id}/read | 登录；只读自己的提醒，其他用户 ID 返回 404 |
| PUT /me/notifications/read-all | 登录；{throughId} 限定已读上界，保留新到消息 |

前端新增 `ReleaseCalendar.tsx`、`NotificationInbox.tsx`、`ScheduleManager.tsx` 与 `releases.ts`，复用现有 Modal、api 和播放器。通知携带 episodeId，通过播放器 initialEpisodeId 打开指定集；常规入口继续按观看进度续播。日历与信箱可见时 30 秒刷新，后台排期也可手动同步。动态 API 不加入 Service Worker 缓存。

推荐页由 `RecommendationFeed.tsx` 提供单列卡片流，调用公开的 `GET /api/recommendations`。Repository 在一次查询中复用短剧基础列表，再以用户行为聚合分类偏好：追剧 4 分、收藏 3 分、历史 1 分；播放量、追剧和收藏状态作为辅助分。接口返回 `recommendationScore` 与 `recommendationReason`，不新增画像表，避免为演示规模引入不可审计的黑盒模型。未登录请求返回热播/新剧兜底，登录后按 JWT 用户身份读取关系数据。


## 1. 总体结构

```text
浏览器/PWA
   │ 同源 HTTP
React 19 + TypeScript + Vite
   │ /api
Spring Boot 3.5.6 + Java 21
   │ JdbcTemplate / 参数化 SQL
MySQL 8.4
```

生产构建后的 React 静态文件复制到 Spring Boot 的 `static/`，因此演示服务只需要 Java 和本地 MySQL。开发时 Vite 代理 `/api` 到后端。

## 2. 后端分层

- `AuthController`：注册、登录、当前用户和昵称修改。
- `DramaController`：公开列表、详情、播放计数、点赞、收藏和推荐入口。
- `EngagementController`：观看历史、进度、评论。
- `ReleaseController` / `ReleaseService` / `ReleaseDemoData`：排期、预约、提醒、事务发布和示例计划初始化。
- `EpisodeController`：公开分集、分集进度、追剧列表/关系、管理员分集 CRUD 与状态校验。
- `EpisodeMigration`：启动时幂等迁移旧单视频和观看进度；已迁移内容不会被重新初始化。
- `AdminController`：管理员统计和短剧 CRUD。
- `ProfileMediaController`：用户头像/主页背景上传、图片缩放和资源地址返回。
- `DramaRepository`：列表、详情、过滤、互动计数和推荐分数 SQL。
- `SecurityConfig`：无状态 JWT、角色转换、BCrypt、401/403 JSON 错误。
- `schema.sql`：表、索引、联合唯一约束和外键。

所有 SQL 使用参数绑定；管理员资源 URL 在 Controller 层通过 URI 规则校验。主要关系使用 ON DELETE CASCADE；已发布计划与分集的关系使用 ON DELETE SET NULL。

分集阶段共11张表，之后增加3张发布表和2张评论治理表成为16张；商城首版新增5张表，购物详版再新增7张，评价新增1张，多规格新增3张，当前合计32张。旧表不做破坏性改造：`watch_history` 保留每人每剧的汇总进度，新播放器写入分集进度时在同一事务更新汇总；旧进度接口映射到第一集。详情按最近分集观看时间返回 `resumeEpisodeId/No`。删除某集会级联清理分集进度并重算历史；删除全剧级联清理所有关系。

分集写入、改集、删集和删历史通过短剧行锁串行化，集号还有数据库唯一约束。前端将一次播放会话中的保存请求排队，每个视频组件绑定固定分集，卸载时保存旧集快照，避免快速切集把进度写到新集。跨设备同时观看采用服务端最后到达的保存结果，暂未做多设备冲突合并。

关键索引：用户名唯一、点赞/收藏/历史联合唯一、评论举报 `(comment_id,user_id)` 联合唯一、分类索引、评论 `(drama_id, create_time)` 索引。

## 4. API 契约

公开接口：`GET /api/health`、`GET /api/dramas`、`GET /api/dramas/{id}`、`GET /api/dramas/{id}/comments`、`POST /api/dramas/{id}/view`。

认证接口：`POST /api/auth/register`、`POST /api/auth/login`、`GET /api/auth/me`。

个人资料接口：`POST /api/auth/profile/avatar`、`POST /api/auth/profile/background`，使用 `multipart/form-data` 上传图片，登录后可用。

`PATCH /api/auth/profile` 接收 `{ "nickname": "新昵称" }`，经长度、空白和控制字符校验后，仅更新 JWT 对应用户并返回当前资料。账号和角色不可从该接口修改。超大文件返回 413，缺失文件和不可解码图片返回 400，均带中文错误信息。

互动接口：`PUT/DELETE /api/dramas/{id}/like`、`PUT/DELETE /api/dramas/{id}/favorite`、`GET /api/me/favorites`。

增强接口：`GET /api/me/history`、`PUT /api/dramas/{id}/progress`、`DELETE /api/me/history/{id}`、`POST /api/dramas/{id}/comments`。

管理接口：`GET /api/admin/stats`、`GET/POST /api/admin/dramas`、`PUT/DELETE /api/admin/dramas/{id}`。

| 新接口 | 权限与契约 |
| --- | --- |
| `GET /api/dramas/{id}/episodes` | 公开；按集号返回分集，登录后带本人的进度 |
| `PUT /api/dramas/{id}/episodes/{episodeId}/progress` | 登录；`{progressSec,durationSec}`，验证集属于剧，进度裁剪到时长 |
| `PUT/DELETE /api/dramas/{id}/follow` | 登录；幂等追剧和取消追剧 |
| `GET /api/me/following` | 登录；追剧片单、连载状态、新集及未完集数 |
| `PUT /api/admin/dramas/{id}/series` | 管理员；`{status,totalEpisodes}`，校验全集完整性 |
| `POST /api/admin/dramas/{id}/episodes` | 管理员；`{episodeNo,title,videoUrl}` |
| `PUT/DELETE /api/admin/dramas/{id}/episodes/{episodeId}` | 管理员；改集/删集，验证归属和至少保留一集 |

错误统一返回 `{ "message": "可读错误信息" }`，常用状态码为 400、401、403、404、409。

## 5. 前端结构

新增 `Player.tsx`（分集播放及视频生命周期）、`Following.tsx`（追剧片单）、`EpisodeManager.tsx`（分集后台）、`downloads.ts`（兼容旧缓存的分集键）及 `episodes.css`。播放器已从 `main.tsx` 抽出。

`main.tsx` 负责路由 hash、认证状态、发现/榜单/收藏/历史/后台视图；`Profile.tsx` 负责个人主页、资料编辑、片单搜索和管理；`ProfileImageEditor.tsx` 使用 Canvas 预览裁剪图片，支持指针拖动和可键盘操作的滑块。`Modal.tsx` 复用弹窗及焦点管理；`api.ts` 负责 Token 注入、中文网络错误转换和数量格式化；`style.css` 和 `profile.css` 提供桌面及手机布局。

移动端使用底部导航，播放器采用 `playsInline`，个人中心使用封面背景、圆形头像和收藏/观看记录 Tab。头像与背景通过同源 multipart 接口上传，后端统一缩放为 JPEG 并写入 `uploads/`；短剧分享 URL 为 `/#watch/{id}`；登录用户详情含个人进度，播放器在元数据加载后恢复位置，播放中定期同步。离线片库用本机 Cache Storage 和 `localStorage` 元数据，无需离线 API。

裁剪仅在确认保存时编码 JPEG（头像 512×512、背景 1600×900）并提交，取消只释放本地预览资源。服务端继续独立校验与重编码，不信任客户端文件类型。新地址保存成功后的旧文件清理失败只记录日志，不把已完成的上传返回为失败。Vite 开发代理包含 `/api` 和 `/uploads`，保证开发环境回显。

## 6. PWA 方案

`manifest.webmanifest` 设置名称、192/512px PNG 图标、`standalone` 显示模式和竖屏方向。Vite 生成 `asset-manifest.json`，`sw.js` 安装时预缓存 HTML、JS、CSS 等 App 壳资源；带哈希的构建资源优先读缓存，避免断网重载白屏。`mujian-app-v3` 升级仅清理旧 App 壳缓存，保留 `mujian-offline-v1`。视频和音频不自动写入 App 壳缓存，用户主动下载的媒体由独立缓存管理，支持 HTTP Range 206/416 和离线拖动；`/api/` 动态接口不缓存。认证网络错误不当作 401 清理 Token，重新联网后再恢复用户状态。

当前方案满足“可安装 App”体验，但不是原生安装包。要发布 APK/IPA，需要引入 Capacitor、Android/iOS SDK、签名和应用商店配置。

`scripts/verify-episodes.mjs` 验证 28 项分集接口规则，`scripts/verify-episodes-ui.mjs` 验证播控、追剧和后台，截图存 `docs/screenshots/episodes/`。2026-10-01 分集阶段因 WSL 资源不足使用 Windows 构建；2026-10-03 商城详版已在 WSL Ubuntu 中完成 TypeScript/Vite/Maven 构建，运行与 HTTP/Edge 验收沿用本机 Java/MySQL。
